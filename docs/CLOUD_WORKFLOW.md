# Один чат, Codex Cloud і GitHub

## Розподіл роботи

Координаційний чат читає актуальний GitHub, перевіряє дослідницькі підстави, приймає редакційні рішення й рецензує PR. Codex Cloud працює з вибраною гілкою у власному контейнері: редагує, тестує, збирає, готує PR. GitHub зберігає прийняті джерела й результати. Перенесення ZIP між чатами не є основним процесом. Codex Cloud не успадковує файли, Safari/Xcode або авторизацію CLI з Mac.

Робоча база, перевірена для цього документа: main на `d7d9545b9d3052a3f056514277e40e37e9c36c8a`. Демо опубліковано. Перед новою задачею перечитати реальний HEAD: ця дата не робить старий SHA вічно актуальним. Нова гілка з правилами — ще не новий реліз сайту.

## Запуск без ноутбука

У Codex Cloud вибрати `mathewfromua/asp24-nggroup-demo-research` і потрібну гілку. Для цього етапу — `chore/cloud-editorial-foundation`, доки її не прийнято в main. Перевірити Environment: доступ саме до цього repo; Node 24 для збігу з чинним CI; Python 3.12 для генератора; setup і maintenance для зафіксованих залежностей. Перевірити доступні версії перед встановленням; не підміняти pin без записаного рішення.

Репозиторій може містити setup-скрипти, але сам факт коміту не налаштовує Environment в акаунті. Налаштування доступу/мережі й запуск першого тесту виконує власник через вебінтерфейс, якщо інтеграція агента не має таких прав. Не передавати PAT у звичайний чат або у файли. Наявність GitHub-конектора в ChatGPT не доводить, що Cloud Environment вже підключений.

Setup встановлює залежності й браузери у дозволеному середовищі. Мережевий доступ фази агента задається окремо; за можливості обмежувати потрібними доменами. Не зберігати setup secrets для доступу агента. Для передачі змін користуватися штатним результатом Cloud/PR, не вважати `gh auth status` на Mac передумовою Cloud-роботи.

Початковий Cloud smoke: поточні `npm test`, `npm run build`, `npm run verify`, HTTP-preview. Окремий smoke — генерація обох звітів із source. Звичайний build зараз бере готові PDF/HTML, тому його успіх не доводить можливості редакційної генерації в Cloud. Підготовку шрифтів див. reports/AGENTS.md.

## Розподіл прав і налаштування GitHub

Після перевірки працездатності PR-checks запропонувати ruleset для main: PR, required build із реальною назвою check, закриті дискусії, заборона force push/видалення. Для одного власника 0 обов’язкових сторонніх approvals. Не вимагати post-deploy check на PR. Ruleset застосовувати тільки з дозволеним admin-доступом; YAML із бажаними settings сам по собі нічого не вмикає. Не створювати постійний admin-token для обходу браку прав.

Перевірити поточні Dependabot alerts, dependency graph, secret scanning/push protection і code scanning. У межах дозволів підготувати конфігурацію оновлень GitHub Actions та Python; npm додати після появи залежностей. Запропонувати мінімальний SECURITY.md і перевірити канал приватного повідомлення перед обіцянкою такого каналу. Не вмикати платні сервіси/розширені runners без дозволу. Не прирівнювати зелений security screen до аудиту безпеки.

Pages лишається основним хостингом статичного демо. PR не має автоматичного окремого публічного URL. Для перевірки гілки спочатку достатньо HTTP-preview/артефактів CI; не розгортати неперевірений PR із доступом до secrets.

## Release без залежності від локального ZIP

Відсутність Release не означає відсутності опублікованого демо. Зібрати потрібний комплект можна заново з точного commit у Cloud або GitHub Actions: вихідний код, dist, PDF/HTML, README, manifest та стислий протокол. Не включати приватний архів, font binaries і caches. Новий ZIP отримає власний hash; не обіцяти hash попередньої локальної копії.

Фінальний Release має вказувати точний tag/commit, прикладені artifacts і фактичні межі. Операція запису потребує відповідних прав. Якщо автоматична перевірка відхилила workflow із contents:write, не обходити її новим замаскованим workflow. Зберегти успішно зібраний артефакт CI й передати власнику одну дозволену вебоперацію створення/прикріплення Release або погодити мінімально привілейовану реалізацію окремо. Постійний широкий token не потрібний.

## Коли потрібна локальна дія

| Клас | Що може зробити Cloud | Що лишається власнику |
|---|---|---|
| ACCOUNT_PERMISSION | Підготувати скрипт/точне налаштування, перевірити доступні права | Підключити repo/Environment, погодити admin-setting у вебінтерфейсі; це не обов’язково Mac |
| MACOS_REQUIRED | Підготувати сценарій, тестові дані, очікування й команду | Справжній Safari, Xcode/Simulator або VoiceOver на доступному Mac |
| DEVICE_REQUIRED | Перевірити WebKit/mobile viewport і HTTPS URL | Дотик, системна клавіатура й нативні переходи фізичного iPhone |
| SOURCE_MISSING | Відшукати відкриті копії й зберегти вторинну атрибуцію | Надати недоступний приватний доказ лише коли без нього змінюється потрібний висновок |

Локальне передавання містить Issue/гілку/HEAD, preconditions, кілька точних кроків, очікуваний результат, потрібний доказ та умову повернення до Cloud. Відновлювати весь старий локальний Codex не потрібно. Незалежні редакційні PR через Apple-блокер не зупиняються.

GitHub Mobile придатний для перегляду файлів, Issues, обговорення й рецензії PR. Налаштування Cloud, rulesets, безпеки й оформлення Release зручніше робити у вебверсії, доступній також з телефона. Звичайні коміти, тести й збірки виконуються в хмарі; ноутбук потрібний для конкретного локального обладнання/середовища, не для GitHub загалом.

## Новий Cloud і Legacy

Цей прохід виконується прямою активною задачею нового Cloud, не onboarding і не Mac. Поля нового Environment — **Install script** (залежності) та **Start skill** (короткі інструкції). Зміна reusable setup потребує Save/Republish; чинна задача не отримує її автоматично. Setup не редагує репозиторій і не перегенеровує звіти на кожний запит.

Наявні GitHub `@codex` workflows можуть використовувати Legacy Environment. Вони не є вимогою створити ще одне середовище для цього проходу. AGENTS задають правила, але не встановлюють пакети й не надають account permissions. Кореневі інструкції доповнюються адресними reports/research; спосіб їх завантаження й доступний ліміт залежать від tool surface, однакове читання всіма інтеграціями не заявляється.
