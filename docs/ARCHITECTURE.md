# Архітектура: від демонстрації до переносного коду

Статус: **запропонований цільовий напрям**, не міграція, вже виконана в main. Основа рішення — дерево d7d9545 і вимога працювати через Cloud, передавати підтримуваний код та зберегти прийняті огляди. Зовнішнього backend магазину не потрібно.

## Поточний стан

Native ESM, CSS і власний build-static.mjs дають працездатний статичний dist. GitHub Actions перевіряє, публікує й звіряє HTTPS-байти. reports/content.json годує Python-генератори; build демо бере готові PDF/HTML. Корисні контракти і тести вже існують.

Є конкретні точки для розвитку: власне переписування import-шляхів regex у builder; великий app.js; розділення DOM/стану/сховища; відтворення PDF без приватного Mac; перевірка застарілих артефактів; браузерні регресії. Розмір файла сам по собі не є виміром швидкості або доказом дефекту.

## Рекомендований цільовий стек

- **TypeScript strict + Vite**: стандартна збірка, явний base path, типові dev/build/preview, перевірка типів окремою командою. Vite transpile не замінює typecheck. Підтримувані стабільні версії перевірити та зафіксувати lockfile під час реалізації.
- **React для інтерактивного UI**, поступово: каталог, порівняння, проєкти. Це запропонована точка зближення компонентів, не вимога негайно переписати все. Один пілот має показати виграш у зрозумілості/тестуванні без втрати функцій. Логіку не прив’язувати до React.
- **Звичайний семантичний HTML і CSS tokens** для оглядів, загальних сторінок і тем. Не додавати важку UI-систему лише заради стилю. Svelte/Vue теж придатні; немає доказу, що заміна бренду бібліотеки сама усуває поточні проблеми.
- **Playwright** для Chromium/Firefox/WebKit, component/unit tests для логіки. Зберегти чинні Node tests; перехід на інший test runner допустимий лише без втрати assertions. Додати runtime-валідацію імпорту/контенту на зовнішніх межах; типів TS недостатньо для недовіреного JSON.
- **Python-генератор звітів** з pinned залежностями та відтворюваними зовнішніми шрифтами. Заміна PDF-рушія не залежить від React. Для R42 дослідити семантичний HTML → tagged PDF (наприклад WeasyPrint) на контрольному розвороті; підтримка опції PDF/UA не гарантує валідного документа.

## Межі модулів

Це цільове розміщення, а не вимога перейменувати всі шляхи в одному PR:

```text
src/domain/       чисті правила пошуку, відбору, порівняння, кількостей
src/data/         synthetic fixtures, contracts, mapping ідентифікаторів
src/adapters/     URL, localStorage, export/import, можливі майбутні API
src/ui/           компоненти, доступність, подання стану
src/styles/       tokens і компактні теми ASP24 / NG Group
reports/          джерело, генератори й перевірки PDF/HTML
research/         прийняті рішення та точна карта доказів
public/           дозволені статичні файли
scripts/          cloud setup, build, verify, package
```

Domain не імпортує DOM, React або localStorage. Приклад контракту: `filterProducts(products, criteria)`, `compareProducts(candidates, fields)`, `calculateCart(lines)`; це ілюстративні назви, не вже наявний API. Money — суми в мінімальних грошових одиницях; кількість/метраж — окремі типи. Відсутність параметра, 0, not-applicable та конфлікт джерел не зливаються. Модель/виконання мають стабільну ідентичність, vendor SKU — окреме зіставлення.

Для наступного розробника передаються контракт, приклад використання, тестові дані й тести, а не HTML із прихованими глобальними залежностями. Це робить перенесення передбачуваним; буквальне Ctrl-C/Ctrl-V не підключить інший каталог, CRM або backend автоматично.

## Порядок міграції й запобіжники

1. Завершити редакційне приймання та Cloud-відтворюваність; окремо зафіксувати стабільний tag.
2. Окремий PR `chore/vite-typescript`: замінити саморобну збірку, додати TS поступово, не змінюючи UX і не переносячи весь source одразу. Перевірити корінь і Pages-підкаталог, старі deep links, MIME і звіти. Стару збірку прибрати після parity.
3. Окремий PR `refactor/domain-boundaries`: відділити pure logic і storage adapters; регресійні fixtures старого імпорту, malformed JSON, quota/write failures.
4. Окремий PR `feat/react-comparison-pilot`: один сценарій шести кандидатів і пари з add/replace/remove/undo/reload, збереження фокуса й чернетки. Порівняти з baseline за ідентичними даними. Повна міграція UI — тільки після приймання пілота.
5. Окремо графіка товарів та візуальне вдосконалення: цілісні легкі ілюстрації, різні силуети за категоріями, жодних неправдивих характеристик або випадкових emoji. Не змінювати дослідницькі скриншоти на «красивіші» реконструкції.

До й після пілота виміряти transferred bytes (raw/compressed окремо), запити, час інтерактивного сценарію в однаковому лабораторному середовищі, focus/reload/keyboard/overflow. Не встановлювати вигаданих baseline або заяв приросту конверсії. Приймати лише пояснений бюджет змін, не «новіше значить краще».

## Що не додаємо зараз

Немає підстав для Next.js server, microservices, Kubernetes, БД, платежів, акаунтів, monorepo-оркестратора чи окремої CMS. Огляди повинні мати статичний читабельний HTML; демокаталог не потрібно перетворювати на SEO-магазин. Перехід до production ecommerce — інший проєкт з іншими контрактами та безпекою.

Shareability: статичні title/description, Open Graph/social-card для проєкту й оглядів, правильний canonical власної публікації; явна позначка демо. Одна hash-route SPA не дає різні server metadata кожному товару автоматично. Якщо потрібні окремі картки поширення, потрібні окремі статичні URL/prerender, а не тільки JS після завантаження. Перевіряти фактичне відображення, не обіцяти всі платформи.
